# 压缩时保留的 N 轮怎么算？（DeepSeek V3.1 为例）

核心认知一句话：**"留 N 轮"不是按轮设计的，是按 token 预算倒推出来的。**

---

## 机制：三步

**第一步：定 token 预算，不定轮数**

```
keepRecentTokens ≈ 2 万 token
```

DeepSeek Harness 官方默认 `retainRatio = 0.16`（窗口的 16%），128K × 16% ≈ 20K——和 Pi 的绝对值 20000 收敛到同一个数。

为什么按 token 不按轮？因为**每轮体量天差地别**：一轮"好的"十几个 token，一轮"跑测试看报错"可能带 8000 token 工具输出。按轮数留，等于对长度完全失控。

**第二步：从最新往回累计，找切点**

```
从最新一条往前逐条累加 token，加到接近 2 万预算停手
切点之前 → 做摘要
切点之后 → 留原文
```

**第三步：切点必须合法——不拆 tool call / tool result 对**

一轮往往是：用户 → 助手发起 read → 工具结果 → 助手发起 edit → 工具结果 → 助手解释。必须整轮整轮保留，不能在"助手说读文件"和"文件内容"中间切开，否则模型上下文断片。

---

## 为什么正好是 2 万？两个约束夹出来的

**下界：盖住"当前进行中的操作"**

压缩常发生在任务做到一半。尾巴的职责是保证进行中的编辑、最近的工具调用格式以原文存活——否则就是社区反馈过的"压缩后忘掉刚才的编辑"、工具调用"节奏感"退化。一个进行中的子任务单元 ≈ 3-5K，20K 能盖 3-5 个。

**上界：尾巴太大，压缩就白压**

```
128K 窗口，触发时约 99K：
  尾巴 20K（16%）→ 压掉 79K，腾出 ~75% 窗口 ✅
  尾巴 60K（47%）→ 只压掉 39K，干几轮又触发 → 压缩循环（连压）❌
```

尾巴超过窗口两成，摘要省下的空间全被吃回去。

两套独立实现（Pi 绝对值、DeepSeek 比例值）在 128K 窗口收敛到同一个数，说明是稳定解，不是拍脑袋。

---

## 折算成轮数（"7-10 轮"的真身）

| 场景 | 单轮体量 | 2 万 token 保住 |
|---|---|---|
| 纯对话 | ~300-800 token | 15~20 轮 |
| 正常编码（读文件+改+跑测试） | ~2-3K | **7~10 轮** |
| 大工具结果的轮 | ~5-8K | 3~5 轮 |

**"7-10 轮"是正常编码场景下 2 万 token 的观感值**，是结果不是参数。面试说"保留 7-10 轮"会被追问穿；说"留约 2 万 token 最近原文，往回找合法切点"才是实现层的答案。

---

## 面试一句话

> "留 N 轮"不是按轮算的：给一个约 2 万 token 的预算（DeepSeek Harness 是窗口的 16%，Pi 是绝对值 2 万，收敛到同一个数），从最新往回累计找到切点，且不拆 tool call/result 对。2 万来自两个约束——盖住进行中的子任务原文、又不超过窗口两成防压缩循环。折成轮数，正常编码场景观感上就是 7~10 轮。
