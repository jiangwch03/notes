# Redis Stream 工作原理

## 1. 本质

Redis Stream 是 Redis 5.0 引入的数据结构，本质是一个**持久化的、支持消费组的有序消息队列**。可以把它理解为 Redis 版的 Kafka——既支持消息追加写入，又支持多消费者分组消费。

## 2. 消息 ID

每条消息写入时，Redis 自动生成一个唯一 ID，格式为：

```
<毫秒时间戳>-<序列号>
```

例如 `1698765432100-0`。

- 时间戳部分 = 写入时的毫秒级时间
- 序列号 = 同一毫秒内递增，用于去重
- 消息 ID 全局递增有序，天然就是消息的顺序标识

## 3. 底层存储

Redis Stream 的底层实现基于 **radix tree（压缩前缀树）**：

```
radix tree (按毫秒时间戳组织)
│
├─ 节点 key: "1698765432100" (毫秒时间戳)
│  └─ listpack (紧凑链表)
│     ├─ 1698765432100-0 → {field1: value1, field2: value2}
│     ├─ 1698765432100-1 → {field1: value3, field2: value4}
│     └─ 1698765432100-2 → {field1: value5, field2: value6}
│
├─ 节点 key: "1698765432101" (下一个毫秒)
│  └─ listpack
│     ├─ 1698765432101-0 → {field1: value7}
│     └─ 1698765432101-1 → {field1: value8}
│
└─ 节点 key: "1698765432102"
   └─ listpack
      └─ 1698765432102-0 → {field1: value9}
```

**结构说明：**

- **radix tree 的 key** = 消息 ID 的毫秒时间戳部分（前缀压缩）
- **每个 radix tree 节点** = 存储相同毫秒时间戳的所有消息
- **节点内部用 listpack（紧凑链表）** 连接这些消息，按序列号有序排列
- **相同前缀的 ID 共享节点**，节省内存
- **消费组的 PEL** 也用独立的 radix tree 维护，结构类似

Redis 没有 Kafka 那种 `topic` 类型。项目里的 topic 是业务给某一路消息起的名字，落到 Redis 上就是 **一个 Stream key**。Pub/Sub 对应的是 **channel**（只转发，不落树）。

**不是整库共用一棵树。** 一个 Stream key 自己一棵 rax。树里按消息 ID 的时间戳前缀压缩，同一毫秒的消息再进那个节点的 listpack。换一个 key，就是另一棵树。PEL 是这个消费组自己的一棵 rax，和消息本体那棵分开。

```
Redis 实例
├─ key: log:operation:knowledge-admin   ← 一棵 rax
├─ key: log:login:knowledge-admin       ← 另一棵
├─ key: embedding.pending               ← 再一棵
└─ key: 某个 Pub/Sub channel            ← 没有树，只转发
```

## 4. 消息发送与消费整体流程

### 4.1 生产者写入

生产者往一个 Stream 里追加消息，每条消息由 Redis 自动生成一个全局唯一的递增 ID。消息本身是一组 field-value 键值对，Redis 把它追加到 Stream 的尾部。

写入的同时可以带上裁剪策略，比如"只保留最近 N 条"，防止 Stream 无限膨胀把内存撑爆。

**关键点：** 写入是原子的、有序的。不管多少个生产者并发写，Redis 单线程模型保证消息 ID 严格递增，不存在乱序。

### 4.2 消费组与消费者

Stream 创建后，可以挂多个**消费组**。每个消费组代表一组协同工作的消费者，它们共同分担这个 Stream 里的消息。

```
Producer ──写入──▶ Stream
                     │
              ┌──────┴──────┐
              │  消费组 A     │  ← 独立消费，互不影响
              │  C1  C2  C3  │
              └─────────────┘
              ┌─────────────┐
              │  消费组 B     │  ← 也独立消费，各自拿到完整副本
              │  C4  C5      │
              └─────────────┘
```

- **同组内**：消息被分发给组内某一个 consumer，实现负载均衡
- **不同组**：每组都拿到完整的消息流，实现广播

### 4.3 PEL：消费组级别的待确认清单

**PEL（Pending Entries List）是消费组级别的，不是消费者级别的。**

一个消费组共享一个 PEL，PEL 记录的是这个组内所有"已分发但未 ACK"的消息。每条 PEL 条目会标注消息当前分配给了哪个 consumer，但 PEL 本身不属于任何一个 consumer。

```
消费组 A 的 PEL（属于整个组，不属于某个 consumer）
│
├─ 消息 100-0 → 归属 C1, 投递 1 次, 最后投递时间 10:30:05
├─ 消息 100-1 → 归属 C2, 投递 1 次, 最后投递时间 10:30:06
├─ 消息 100-2 → 归属 C1, 投递 2 次, 最后投递时间 10:30:10  ← C1 处理慢，被重投过
└─ 消息 100-3 → 归属 C3, 投递 1 次, 最后投递时间 10:30:08
```

可以按 consumer 维度查看 PEL 的子集：

```
消费组 A 的 PEL 中：
  ├── C1 待处理的: [100-0, 100-2]
  ├── C2 待处理的: [100-1]
  └── C3 待处理的: [100-3]
```

不同消费组各自维护独立的 PEL，互不影响：

```
Stream key: "log:op"
├─ 消费组 A → PEL_A: {100-0, 100-1, 100-2, 100-3}
├─ 消费组 B → PEL_B: {100-0, 100-1}  ← 独立的 PEL，各自记录各自的进度
└─ 消费组 C → PEL_C: {}               ← 还没开始消费
```

### 4.4 消息分发与确认

消费组内的 consumer 主动去"拉"消息（pull 模型）：

1. consumer 向 Redis 发起读取请求，声明"我是消费组 A 的 C1，给我来几条新消息"
2. Redis 从 Stream 中取出尚未被分配的消息，返回给这个 consumer
3. **消息一旦被某个 consumer 读走，就进入该消费组的 PEL**，Redis 记录下归属和投递时间

consumer 处理完消息后，向 Redis 发送 ACK：

- ACK 之后，消息从 PEL 中移除，这条消息对这个消费组来说就彻底完成了
- 如果没有 ACK，消息会一直留在 PEL 中

### 4.5 超时接管：消费方的责任

**超时接管完全由消费方（应用层）驱动，Redis 只负责维护 PEL 中每条消息的投递时间和投递次数。**

```
消息被 C1 读走 → 进入 PEL_A，归属 C1
    ↓
C1 处理完 → ACK → 从 PEL_A 移除 ✅
    ↓ (如果 C1 挂了/超时未 ACK)
应用层的接管协程定期扫描 PEL_A
    ↓
发现消息 100-0 空闲超过 60 秒（阈值由应用层定义）
    ↓
C2 执行接管 → 消息在 PEL_A 中的归属从 C1 变为 C2，投递次数 +1
    ↓
C2 处理完 → ACK → 从 PEL_A 移除 ✅
```

关键设计：

- **超时阈值**：由应用层定义（比如 60 秒），Redis 不管
- **扫描频率**：由应用层决定（比如每 5 秒扫一次），Redis 不管
- **谁来接管**：应用层自己起后台协程去调接管命令，Redis 不主动推送
- **投递次数**：PEL 记录每条消息被投递了几次，应用层可以据此判断是否需要告警或放弃

这就是 **at-least-once** 语义——消息不会因为某个 consumer 挂了而丢失，但同一条消息可能被多个 consumer 处理，业务层需要自己做幂等。

### 4.6 整体流程图

```
生产者写入消息
      ↓
消息进入 Stream 尾部，分配全局递增 ID
      ↓
消费者主动拉取（pull）
      ↓
Redis 把消息交给某个 consumer，同时记入 PEL
      ↓
  ┌─ consumer 处理成功 → 发 ACK → 消息从 PEL 移除 ✅
  │
  └─ consumer 挂了/超时未 ACK → 消息留在 PEL
                                    ↓
                              其他 consumer 定期扫描 PEL
                                    ↓
                              超时消息被重新分配 → 再次处理
```

## 5. 消息删除与 PEL 清理

### 5.1 消息什么时候从 Stream 中删除？

**消息从 Stream 中删除，与消费者组的消费进度无关。**

消息的删除只取决于：

- **MAXLEN / MINID 裁剪策略**：写入时按数量或 ID 裁剪，不管有没有被消费
- **手动删除**：通过 `XTRIM` 或 `XDEL` 命令主动删除
- **Redis 内存淘汰策略**：如果配置了内存淘汰，可能会删除旧数据

PEL 中的 ACK 只是把消息从 PEL 中移除，表示"这个消费组已经处理完了"，但消息本身还在 Stream 中（除非被裁剪策略删掉了）。

```
Stream 中的消息 100-0
├─ 消费组 A 的 PEL_A 中有这条消息 → A 还没 ACK
├─ 消费组 B 的 PEL_B 中没有 → B 已经 ACK 了
└─ 消息什么时候从 Stream 中删除？→ 取决于裁剪策略，跟消费组无关
```

**常见误解：** 不是"所有消费组都 ACK 了才删除"。每个消费组的 PEL 是独立的，ACK 只是从自己的 PEL 中移除，不影响 Stream 中的消息本体。

### 5.2 PEL 中一直消费失败的消息，Redis 会主动清理吗？

**不会。Redis 不会主动清理 PEL 中的消息。**

原因：

- Redis 不知道这条消息是"处理失败"还是"处理很慢"
- Redis 只记录投递次数和最后投递时间，但不会根据这些信息做任何决策
- 如果 Redis 主动删除了 PEL 中的消息，就破坏了 at-least-once 语义

**那怎么办？**

- **应用层自己判断**：如果投递次数超过阈值（比如 5 次），就认为这条消息"有毒"，主动 ACK 掉（放弃处理）
- **死信队列**：应用层记录一个"死信队列"，把多次失败的消息转移到其他地方，后续人工介入
- **告警**：监控 PEL 中长时间未 ACK 的消息数量，超过阈值就告警

```
消息 100-0 在 PEL_A 中：
  第 1 次投递给 C1 → C1 处理失败，没 ACK
  第 2 次被 C2 接管 → C2 处理失败，没 ACK
  第 3 次被 C3 接管 → C3 处理失败，没 ACK
  ...
  第 5 次投递 → 应用层判断：投递次数 >= 5，认为消息有毒
                → 主动 ACK（放弃处理）
                → 或者转移到死信队列
```

**关键点：** Redis 提供数据（投递次数、最后投递时间），但决策权在应用层。Redis 不会替你做"这条消息失败了太多次，我帮你删了"这种事。

## 6. 裁剪策略（Trimming）

Stream 不会自动删除已消费的消息，需要主动裁剪，否则内存会无限增长：

| 策略 | 说明 |
|------|------|
| 按数量（MAXLEN） | 只保留最近 N 条 |
| 按 ID（MINID） | 删除 ID 小于指定值的所有消息 |
| 近似裁剪（加 `~` 前缀） | 按 radix tree 整块删除，性能更好，可能有少量误差 |

近似裁剪的原理：Redis Stream 底层用 radix tree 存储消息，精确裁剪需要逐条删除再判断节点是否为空，近似裁剪则直接删除整个空节点，减少 CPU 开销。

## 6. 消息丢不丢：落盘和复制

Stream 就是 Redis 里的一种数据。还在内存里的消息，靠 **RDB / AOF** 落盘，靠 **主从复制** 抄到从库。PEL、消费组进度也跟这个 key 绑在一起，一起持久化、一起复制。

要补三句：

1. **没开持久化，重启就没了。** Stream 自己不会单独写盘。AOF 的 `fsync` 是每秒一次时，这一秒里的写入，主库突然挂了也会丢。
2. **复制默认是异步的。** 主库写完就回客户端，从库可能还没收到。主库这时挂了，没抄过去的那几条就没了。要更稳得等从库确认（`WAIT`），代价是写入变慢。
3. **业务上的“丢”经常不是这两套。** `MAXLEN` 裁剪会把旧消息从 Stream 里删掉，哪怕某个消费组还没读完。消费组靠 PEL + ACK 保证至少处理一次，这是消费语义，不是落盘。

消息还在 Stream 里时，丢不丢看 Redis 的落盘和复制；裁掉了、ACK 完了，就跟这两套无关了。

## 7. 与 Pub/Sub 的区别

| 特性 | Pub/Sub | Stream |
|------|---------|--------|
| 消息持久化 | 不持久化，发完即丢 | 存在对应的 Stream key 里，随 RDB/AOF 落盘、随主从复制 |
| 消费确认 | 无 | ACK 确认机制 |
| 消费组 | 不支持 | 支持 Consumer Group |
| 历史消息回放 | 不支持 | 支持（从任意位置读） |
| 消息 ID | 无 | 自动生成全局有序 ID |
| 可靠性 | 低（消息可能丢失） | 高（at-least-once 保证） |

## 8. 与 Kafka 的对比

| 维度 | Redis Stream | Kafka |
|------|-------------|-------|
| **架构** | 单节点内存队列（可主从复制） | 分布式集群，多分区多副本 |
| **消息存储** | radix tree（内存） | 磁盘顺序写 + 页缓存 |
| **消息保留** | MAXLEN/MINID 裁剪，不自动删除已消费消息 | retention 策略自动清理已消费消息（默认 7 天） |
| **消费模型** | 消费组 + PEL（Pending Entries List） | 消费组 + offset commit |
| **消息确认** | 手动 ACK，消息从 PEL 移除 | commit offset，标记消费进度 |
| **失败重试** | 应用层扫描 PEL，超时消息被其他 consumer 接管 | consumer 重新 poll 未 commit 的 offset |
| **死信处理** | 应用层判断投递次数，主动 ACK 或转入死信队列 | 应用层判断重试次数，转入死信 topic |
| **消息回溯** | 支持（从任意 ID 开始读） | 支持（从任意 offset 开始读） |
| **吞吐量** | 万级 QPS（单线程） | 百万级 TPS（多分区并行） |
| **延迟** | 微秒级（内存操作） | 毫秒级（磁盘 IO） |
| **可靠性** | 依赖 Redis 持久化（RDB/AOF），异步复制可能丢数据 | 多副本机制，可配置同步复制，数据更安全 |
| **水平扩展** | 不支持分区，单 Stream 性能有上限 | 多分区多 broker，天然支持水平扩展 |
| **消息顺序性** | 全局有序（单 Stream） | 分区内有序，跨分区无序 |
| **适用场景** | 轻量级、低延迟、已有 Redis 基础设施 | 大规模、高吞吐、需要强可靠性 |

**核心区别：**

1. **消息删除机制**
   - Redis Stream：不自动删除，靠 MAXLEN/MINID 裁剪，PEL 与 Stream 独立
   - Kafka：自动删除，retention 策略按时间或大小清理，offset 与消息绑定

2. **消费确认机制**
   - Redis Stream：PEL 记录每条未 ACK 消息，应用层负责超时接管和死信处理
   - Kafka：offset 记录消费进度，consumer 重新 poll 未 commit 的消息

3. **性能与规模**
   - Redis Stream：内存操作，延迟低但吞吐有限，适合中小规模
   - Kafka：磁盘顺序写，吞吐高但延迟略高，适合大规模数据流

**选型建议：**

- 项目已有 Redis，消息量不大（万级 QPS 以内），对延迟敏感 → **Redis Stream**
- 消息量大（百万级 TPS），需要强可靠性和水平扩展 → **Kafka**
- 需要消息回溯、流处理、Exactly-Once 语义 → **Kafka**（生态更成熟）

## 9. 总结

**生产者写 → Stream 有序存储 → consumer 拉取进入 PEL → 处理完 ACK 移除 → 没 ACK 的被接管重处理**，整个流程形成一个闭环，保证每条消息至少被消费一次。

没有全局 topic：一路消息一个 Stream key，一棵自己的 radix tree。消息还在 key 里时，靠 Redis 落盘和主从复制；裁剪和 ACK 是另外两件事。
